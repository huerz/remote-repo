二、严重（会导致功能不可用或数据错误）
------------------------------------------------------------------------
S1. 密码重置对哈希密码无效                                        [仍存在]
  位置：cls_svr/app/api/user_blueprint.py:327（updatePwd）
        cls_svr/app/dao/UsersDao.py:78（updateUserByPwd）
  现状：仍是 if user.upwd == oldpwd 明文比对；新密码以明文写入 new_pwd。
  原因：教材用明文比对，updateUserByPwd 明文写回。
  影响：所有已注册用户都无法改密码；改成功后密码降级为明文，
        且与 register/login 的哈希逻辑冲突（见 N1 / N2）。
  建议：旧密码 check_password_hash 校验，新密码 generate_password_hash 后再存。

S2. 作品评分单位不一致（数据库 0-100，教材按 1-5）                [仍存在]
  位置：cls_svr/app/dao/ClassicsDao.py:99（updateClassicRating）
        cls_clt/src/views/ClassicView.vue:95（initCls）
  现状：classic.rating = max(judge.rating, classic.rating)；
        star.value = clsData.value.rating；全仓无 *20 / /20 换算。
        ClassicView.vue:85 的注释仍写着「比例问题后面再解决」。
  影响：详情页星级最多只显示 5 星（rating=90 也是 5 星）；
        打分后 rating 基本不增长；且 max() 是取最大值不是累加，
        高分作品永远打不动。
  建议：统一单位。方案 A：后端存 0-100，打分时 star*20，展示 rating/20；
        方案 B：把数据库 rating 改成 1-5（需同步改打分与展示）。

S3. 中文文件名头像上传 500（IndexError）                          [仍存在]
  位置：cls_svr/app/api/user_blueprint.py:226（upload）
  现状：fname = str(uuid.uuid4()) + '.' + upname.rsplit('.', 1)[1]
        upname 来自 secure_filename，中文名会被滤成 "png"（无点号），
        第 226 行 rsplit 越界。
        已在项目 .venv 实测：secure_filename('头像.png') → 'png'，必崩。
        且第 224 行 allowed_file 用的是原始文件名，中文名能通过校验，
        正好走到 226 行。
  影响：中文文件名头像无法上传。
  建议：加扩展名兜底（无点号时从原始 filename 取），或统一 uuid + 原扩展名。
        参考 Hi_upload/app.py 里已经做过的兜底写法。


三、高（安全、权限、稳定性）
------------------------------------------------------------------------
H1. 头像上传接口没有登录校验                                      [仍存在]
  位置：user_blueprint.py:214-215
  现状：只有 @user_blueprint.route('/upload', methods=['POST'])，无 @jwt_required()；
        全仓无 before_request / 蓝图级鉴权兜底。
  影响：匿名即可往 images/head 写文件（磁盘占用 / 恶意文件）。
  建议：加 @jwt_required()，并限制文件大小、类型、频率。

H2. v-html 直接渲染作品简介（XSS 风险）                           [仍存在]
  位置：cls_clt/src/views/ClassicView.vue:394
  现状：<el-row><div v-html="clsData.describes"></div></el-row>
        package.json 无 dompurify 等清洗依赖，全仓无 sanitize。
  影响：describes 含 <script> 或 onerror 时会在浏览器执行，存储型 XSS。
  建议：改用 {{ clsData.describes }} 文本插值，或后端清洗 HTML。

H3. 书评顶/踩无去重，可无限累加                                   [仍存在]
  位置：ClassicsDao.py:136-142（updateDiscussTopLow）
  现状：只查 Discuss.query.get(judge.did)，未按 (did, uid) 查 Discussjudges 去重，
        每次都 db.session.add(judge) 并 topcount/lowcount +1。
  影响：顶/踩计数失真。
  建议：按 (did, uid) 查重，同方向不重复、反方向改判。

H4. 作品评分无去重，评价表无限增长                                [仍存在]
  位置：ClassicsDao.py:100（updateClassicRating）
  现状：无条件 db.session.add(judge)，无 (cid, uid) 查重，也无 update 覆盖逻辑。
  影响：classicjudges 表膨胀；叠加 max() 后重复打分对 rating 无二次影响，
        但会持续产生垃圾数据。
  建议：按 (cid, uid) 查重后更新，不重复插入。

H5. 数据库异常被吞，表现为 404 而不是 500                         [仍存在]
  位置：UsersDao.py:41-43（getUserByUid）
  现状：except Exception as e: print(e); pass，隐式返回 None；
        上层 user_blueprint.py:293-298 把 None 映射成 code 404。
        项目内无 logging，只有 print(e)。
  影响：MySQL 未启动时 get-user 返回「操作失败！」/404，
        而不是连接错误，排查困难。
  建议：DAO 记录日志并向上抛，或返回明确的错误码。

H6. 计数 +1 在 NULL 上会 TypeError                                 [仍存在]
  位置：ClassicsDao.py:123（commentscount）
        ClassicsDao.py:139-141（topcount / lowcount）
  现状：classic.commentscount = classic.commentscount + 1 等，全是裸加。
  影响：字段为 NULL 时接口 500。
  建议：(classic.commentscount or 0) + 1。

H7. discuss 为 None 时 for 循环报错                                [仍存在]
  位置：classics_blueprint.py:291（get_discuss）、:399（get_mydiscuss）
  现状：for dis in discuss:，无 (discuss or []) 保护。
  影响：DAO 异常返回 None 时抛 TypeError。
  建议：for dis in (discuss or [])。
